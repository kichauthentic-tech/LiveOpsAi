Đã lập tức cảnh báo user, hướng dẫn đổi mật khẩu DB ngay (coi mật khẩu cũ là compromised bất kể có xóa log hay không) — **không tự ý xử lý/xem thêm secret**, để user tự thực hiện toàn bộ việc đổi mật khẩu.

3. **Lỗi user/password:** lần đầu dùng Session pooler vẫn fail `password authentication failed` — do username phải là `postgres.<project-ref>` (không phải `postgres` trơn) khi qua pooler. 4. **Lỗi version:** sau khi auth pass, `pg_dump` (bản 16 cài mặc định trên Ubuntu runner) từ chối dump từ server Postgres 17.6 (`aborting because of server version mismatch`). Đã verify qua browser thật (Browser pane, không cần đăng nhập vì đây là luồng trước khi có session): màn hình Login hiện đúng nút "Quên mật khẩu?" → bấm vào chuyển đúng sang mode "Quên mật khẩu" (chỉ còn ô Email + nút gửi) → điền email thật, bấm gửi → gọi đúng `supabase.auth.resetPasswordForEmail` (xác nhận qua tab Network: trước đó không có request nào tới `supabase.co`, sau khi bấm có request thật tới đúng project Supabase, lỗi trả về `Failed to fetch` là do **sandbox Claude Browser chặn outbound network ra ngoài `localhost`**, không phải bug code — đúng hạn chế môi trường đã ghi nhận ở các giai đoạn trước, không phải lỗi ứng dụng) → nút "← Quay lại đăng nhập" đưa đúng về form đăng nhập ban đầu.
- **Chưa verify được (cần môi trường có network thật + tài khoản CEO thật để đăng nhập):** (a) gửi email đặt lại mật khẩu thật có tới hộp thư không (phụ thuộc network sandbox ở trên), (b) bấm link trong email thật có đúng bắn event `PASSWORD_RECOVERY` và hiện `ResetPasswordScreen` không, (c) luồng đổi tên/đổi mật khẩu trong tab "Tài Khoản Của Tôi" khi đã đăng nhập thật (form đã build đúng theo pattern các module khác, tái dùng `handleUpdateUser`/`updateUserProfile` đã verify từ Giai đoạn 4, nhưng chưa tự tay bấm thử). **Việc còn treo:** user tự đăng nhập, vào "Tài Khoản Của Tôi", thử đổi tên (xác nhận sidebar/header đổi theo ngay), thử đổi mật khẩu (đăng xuất rồi đăng nhập lại bằng mật khẩu mới để chắc chắn), và thử trọn vẹn luồng quên mật khẩu từ email thật.

## Quy ước kỹ thuật cần theo khi làm tiếp
- Mỗi entity migrate sang Supabase: tạo `src/lib/db/<entity>.ts` với 4 hàm CRUD + mapper (xem 4 file đã có làm mẫu: talents/studios/equipments/sessions)
- Component UI giữ nguyên (camelCase), chỉ đổi lớp persistence trong App.tsx
- Xóa `MOCK_X` khỏi `mockData.ts` sau khi migrate xong module đó
- RLS pattern: đọc = mọi authenticated user, ghi = chỉ role `ceo`/`operations` (xem cuối file `0001_init.sql`)
- Khi 1 entity liên kết FK tới entity chưa migrate (vd sessions → brands), đừng ép FK: thêm cột `<entity>_name` denormalized song song, chỉ set cột `_id` khi giá trị là UUID hợp lệ — xem pattern `asUuidOrNull` trong `sessions.ts`
- Với bảng con 1-nhiều (vd `session_skus`), chiến lược đơn giản nhất khi update là xóa hết theo `session_id` rồi insert lại toàn bộ mảng — không cần diff item-level ở giai đoạn này
- File migration mới phải được user tự áp dụng lên Supabase (chưa `supabase link` trong môi trường này) — luôn nhắc rõ trong response khi tạo migration mới
- Nếu entity nào đó có cột tham chiếu tới `auth.users` (không phải bảng thường): KHÔNG thể CRUD trực tiếp bằng anon key như các bảng khác — phải tạo/xóa qua Supabase Admin API (`service_role` key), và key đó chỉ được sống ở server (`server.ts`), không bao giờ dùng biến `VITE_*` cho nó. Xem pattern đầy đủ ở Giai đoạn 4 (`src/lib/db/users.ts` + endpoint `/api/admin/users/*` trong `server.ts`).
