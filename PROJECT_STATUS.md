Đã lập tức cảnh báo user, hướng dẫn đổi mật khẩu DB ngay (coi mật khẩu cũ là compromised bất kể có xóa log hay không) — **không tự ý xử lý/xem thêm secret**, để user tự thực hiện toàn bộ việc đổi mật khẩu.

3. **Lỗi user/password:** lần đầu dùng Session pooler vẫn fail `password authentication failed` — do username phải là `postgres.<project-ref>` (không phải `postgres` trơn) khi qua pooler. 4. **Lỗi version:** sau khi auth pass, `pg_dump` (bản 16 cài mặc định trên Ubuntu runner) từ chối dump từ server Postgres 17.6 (`aborting because of server version mismatch`). ## Quy ước kỹ thuật cần theo khi làm tiếp
- Mỗi entity migrate sang Supabase: tạo `src/lib/db/<entity>.ts` với 4 hàm CRUD + mapper (xem 4 file đã có làm mẫu: talents/studios/equipments/sessions)
- Component UI giữ nguyên (camelCase), chỉ đổi lớp persistence trong App.tsx
- Xóa `MOCK_X` khỏi `mockData.ts` sau khi migrate xong module đó
- RLS pattern: đọc = mọi authenticated user, ghi = chỉ role `ceo`/`operations` (xem cuối file `0001_init.sql`)
- Khi 1 entity liên kết FK tới entity chưa migrate (vd sessions → brands), đừng ép FK: thêm cột `<entity>_name` denormalized song song, chỉ set cột `_id` khi giá trị là UUID hợp lệ — xem pattern `asUuidOrNull` trong `sessions.ts`
- Với bảng con 1-nhiều (vd `session_skus`), chiến lược đơn giản nhất khi update là xóa hết theo `session_id` rồi insert lại toàn bộ mảng — không cần diff item-level ở giai đoạn này
- File migration mới phải được user tự áp dụng lên Supabase (chưa `supabase link` trong môi trường này) — luôn nhắc rõ trong response khi tạo migration mới
- Nếu entity nào đó có cột tham chiếu tới `auth.users` (không phải bảng thường): KHÔNG thể CRUD trực tiếp bằng anon key như các bảng khác — phải tạo/xóa qua Supabase Admin API (`service_role` key), và key đó chỉ được sống ở server (`server.ts`), không bao giờ dùng biến `VITE_*` cho nó. Xem pattern đầy đủ ở Giai đoạn 4 (`src/lib/db/users.ts` + endpoint `/api/admin/users/*` trong `server.ts`).
- Khi 1 quy trình có bước "nháp trước, chốt thành entity thật sau" (vd đăng ký ca → chốt thành session): đừng tạo entity thật ngay từ bước nháp — tách 1 bảng riêng cho trạng thái nháp (`shift_slots`), chỉ insert vào bảng entity thật ở bước chốt, và lưu lại FK trỏ ngược (`shift_slots.session_id`) để tra. Xem Giai đoạn 14.
- Đừng gộp 2 khái niệm nghe giống nhau nhưng khác bản chất chỉ vì tên field trùng ("Assistant"): `assistant_id` (role `moderator`, tài khoản ops không lên hình) và `co_host_id` (talent lên hình cùng host, Giai đoạn 14) là 2 cột tách biệt trên `live_sessions` — sinh ra đúng 1 lần bug loại này đã đủ, xem phần "Quyết định thiết kế quan trọng" ở Giai đoạn 14.
- Khi user đưa ra 1 file nguồn thật (Excel, export hệ thống cũ...) làm căn cứ thiết kế: nếu sau đó thảo luận đi tới 1 hướng đổi thiết kế mà không mở lại đúng file đó để đối chiếu, dễ suy luận sai (Giai đoạn 14b — suýt đổi đăng ký ca theo slot cụ thể sang "lưới rảnh chung", hoá ra sai khi mở lại Excel gốc bằng `openpyxl` thấy vẫn là đăng ký theo từng dòng slot). Trước khi implement 1 pivot thiết kế dựa trên suy luận trừu tượng, mở lại file nguồn (nếu còn) để kiểm chứng bằng dữ liệu thật.
